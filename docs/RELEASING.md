# Releasing

## Private review

Keep repository visibility **private** until the owner approves public release. Do not submit it to the community directory during review.

The release workflow runs on version tags and creates a **draft** GitHub release containing `main.js`, `manifest.json`, and `styles.css`. Draft assets are for authenticated review and manual installation; they are not a BRAT distribution channel.

## Prepare a version

1. Update `version` in `package.json` and `manifest.json` together.
2. Add that version to `versions.json`, with the minimum compatible Obsidian version.
3. Run `npm install --package-lock-only` to refresh package metadata.
4. Update `CHANGELOG.md` and record device validation.
5. Run `npm run check` and `npm run verify:release`.
6. Commit the source, push the version tag without a `v` prefix (for example `0.3.0`), and inspect the draft release generated by CI.

The workflow rejects a tag that does not match the manifest version. Release binaries are generated from the tagged source and are not committed.

## Public release, after owner approval

1. Complete desktop and mobile validation, or change `isDesktopOnly` if mobile support cannot be confirmed.
2. Add screenshots captured in a synthetic test vault if useful. Confirm the plugin ID is still available in the directory.
3. Change repository visibility only with owner approval, then publish the reviewed draft release.
4. Follow the current [official submission guide](https://docs.obsidian.md/Plugins/Releasing/Submit%20your%20plugin): sign in at [community.obsidian.md](https://community.obsidian.md), connect GitHub, add the plugin, resolve review feedback, and publish.

The manifest at the repository's default branch and the GitHub release tag must agree. Subsequent versions are distributed through GitHub releases after initial directory approval.
